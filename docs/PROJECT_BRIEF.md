# Web Mini Game Arcade プロジェクト企画書

## 1\. プロジェクトの目的

ブラウザから無料で遊べる多数の小規模ゲームを集めた「Webゲームセンター」を構築する。

最終的には100種類以上のゲームを収録し、各ゲームを短時間で遊べるようにする。

このプロジェクトでは、単にゲーム本数を増やすのではなく、

- 短時間でも面白い
- もう一度遊びたくなる
- 操作説明をほとんど読まなくても遊べる
- PCでもスマートフォンでも遊べる
- ロードが速い
- ゲームごとに異なる体験がある
- ランキングやスコア更新によって再プレイしたくなる

ことを重視する。

100本という本数は目標であり、低品質なゲームを大量生成することを目的としない。

品質を満たさないゲームは公開しない。

---

# 2\. 長期的な開発方針

開発は以下の3段階で進める。

## Phase 1：人間主導による基準作り

ユーザーとChatGPTでゲーム案を作る。

そのゲーム案をCodexが実装する。

ユーザーが実際にプレイして、

- 面白さ
- 操作感
- 難易度
- テンポ
- リトライしたさ
- UI
- CREDITシステム

などを評価する。

評価を反映してゲームを改善する。

最初の数本はこの工程を繰り返す。

---

## Phase 2：共通ゲーム仕様の確立

完成したゲームから共通要素を抽出し、

`GAME_COMMON_SPEC.md`

を作成する。

将来的には少なくとも以下を共通仕様化する。

- ゲーム開始方法
- CREDIT管理
- ゲームオーバー
- リトライ
- スコア
- ハイスコア
- ランキング
- PC操作
- スマートフォン操作
- サウンド
- ミュート
- ポーズ
- 画面サイズ対応
- ロード
- Analyticsイベント
- Rewarded Ad連携
- エラー処理
- UI
- アクセシビリティ
- パフォーマンス基準

ただし、最初からすべて共通化しない。

実際に複数のゲームを制作した結果から共通仕様を決定する。

---

## Phase 3：Codex主導の自律開発

共通仕様が十分安定した後は、

Concept
↓
Prototype
↓
Implementation
↓
Automated Test
↓
Game Feel Review
↓
Revision
↓
QA
↓
Human Playtest

までをCodex中心で実施する。

将来的な基本ループは以下。

1. Concept Agentが新しいゲーム案を複数考案
2. Main Agentが既存ゲームとの重複を確認
3. 実装候補を決定
4. Gameplay Agentが実装
5. Game Feel Agentがゲーム性をレビュー
6. QA Agentが技術的品質をレビュー
7. 必要ならGameplay Agentが修正
8. 自動テスト
9. プレビュー版作成
10. 人間が最終プレイ
11. 合格した場合のみ公開候補とする

最終的には、人間は

「遊んで面白さを判断する」

ことに最も時間を使える状態を目指す。

---

# 3\. ゲームの基本思想

ゲームは「広告を見るための装置」にしない。

最優先事項はゲームそのものが面白いことである。

広告収益は、

「無料で遊び続けるための自然な仕組み」

として組み込む。

プレイヤーが

「もう一回やりたい」

と思った結果として広告を見る構造を目指す。

---

# 4\. CREDITシステム

基本CREDITは

3 CREDIT

とする。

原則として、

ゲームオーバー
↓
CREDIT \-1

とする。

CREDITが残っている場合は、そのまま再挑戦できる。

CREDITが0になった場合、

「広告を見ると \+3 CREDIT」

という選択肢を表示する。

実際の広告システムは後日実装する。

初期開発段階ではRewarded Adを抽象化したStubを使用してよい。

例：

`requestRewardedCredit()`

成功時：

`+3 CREDIT`

将来広告SDKを変更してもゲーム本体を修正しなくて済む構造にする。

---

# 5\. 1プレイの想定時間

基本的な目安は、

1 CREDITあたり
約1〜3分

とする。

したがって3 CREDITで、

約3〜9分

遊んだ後に最初の広告機会が発生することを基本とする。

ゲームジャンルによって例外は許容する。

---

# 6\. ゲームジャンル

特定ジャンルに限定しない。

例：

- アクション
- パズル
- シューティング
- タイミング
- リズム
- サバイバル
- ランゲーム
- 物理ゲーム
- カード
- 記憶ゲーム
- 反射神経
- スコアアタック
- ネタゲーム
- 軽量RPG
- 軽量ストラテジー

など。

ただし、ゲーム間で体験が似すぎないようにする。

---

# 7\. 人気ランキング

将来的なゲームポータルでは複数のランキングを実装する。

候補：

- 総合人気
- 今週の人気
- 今日の人気
- 急上昇
- 新着
- 高評価
- プレイ回数
- 平均プレイ時間
- リピート率

単純な累計プレイ数だけで人気を決定しない。

新しいゲームにも露出機会を与える。

---

# 8\. ゲーム内ランキング

可能なゲームではスコアランキングを採用する。

将来的には、

- 今日
- 今週
- 全期間
- 自己ベスト

を表示可能にする。

初期プロトタイプではサーバーを使用しないため、LocalStorageによる自己ベストのみでもよい。

---

# 9\. 技術方針

当面はGodotを使用しない。

基本技術は、

- TypeScript
- Phaser
- Vite
- HTML
- CSS

とする。

必要であれば別の軽量Web技術も使用可能。

ゲームは静的Webサイトとしてビルドできること。

特定サーバーへの依存をゲームロジックに持ち込まない。

バックエンド・広告・ランキング等は後から接続できるよう抽象化する。

---

# 10\. コード構造

ゲーム固有コードと共通コードを分離する。

例：

```text
src/
  core/
    credits/
    input/
    audio/
    storage/
    telemetry/
    lifecycle/

  game/
    player/
    enemies/
    scoring/
    difficulty/
    scenes/
```

ただしGame001の時点では過剰な共通化を行わない。

「将来共通化できそう」という理由だけで複雑な抽象化を作らない。

2〜5本実装した結果を見て共通パッケージへ昇格させる。

---

# 11\. Analytics設計

サーバー実装前でも、将来計測するイベントを定義する。

最低限：

`game_open`

`run_start`

`run_end`

`score`

`credit_used`

`credit_zero`

`reward_offer_shown`

`reward_requested`

`reward_granted`

`retry`

`quit`

将来Analyticsサービスへ置き換えられるよう、

`trackEvent()`

を通して呼び出す。

初期版ではconsoleまたはLocalStorageで構わない。

# 12\. 重要指標

将来特に重要になる指標は以下。

- ゲーム開始率
- 1プレイ時間
- 3 CREDIT消費率
- CREDIT 0到達率
- リトライ率
- Rewarded Ad選択率
- 1人あたりプレイ回数
- 自己ベスト更新率
- 翌日再訪率
- ゲーム間回遊率

ゲームの良し悪しは単純な広告表示数では評価しない。

---

# 13\. サブエージェント構成

Codexの実行環境でサブエージェント機能が利用可能な場合、以下の役割分担を基本とする。

## Main Agent / Lead Developer

責任者。

担当：

- 要件理解
- タスク分解
- サブエージェントへの委任
- 実装方針決定
- 結果統合
- 最終確認

Main Agent自身がすべて実装するのではなく、適切に役割を委任する。

---

## Gameplay Engineer

担当：

- Phaser
- TypeScript
- ゲームロジック
- 操作
- 当たり判定
- 敵
- 難易度
- スコア
- エフェクト
- パフォーマンス

ゲーム本体の実装担当。

---

## Game Feel Reviewer

担当：

「動くか」ではなく「遊びとして成立しているか」を評価する。

確認：

- 最初の10秒が退屈ではないか
- 操作が理解できるか
- ミスした理由が分かるか
- 理不尽ではないか
- 難易度上昇が自然か
- もう一度遊びたくなるか
- スコア更新を狙いたくなるか
- 3 CREDITを使いたくなるか
- テンポが悪くないか
- 演出に気持ちよさがあるか

コード品質とは独立して評価する。

---

## QA / Code Reviewer

担当：

- バグ
- TypeScript品質
- ビルド
- テスト
- 画面サイズ
- タッチ操作
- キーボード操作
- LocalStorage
- CREDIT
- スコア
- FPS
- エラー
- メモリリーク
- 共通インターフェース

を確認する。

---

# 14\. 将来追加するサブエージェント

共通仕様完成後、

## Concept Designer

を追加する。

担当：

- 新規ゲーム案
- 既存ゲームとの重複回避
- 新しい操作方法
- 新しいジャンル
- 既存ゲームの弱点を埋める企画

ゲーム案はタイトルだけではなく、

- Core Loop
- 操作
- 1プレイ時間
- Skill要素
- スコア要素
- Failure条件
- Replay理由
- 独自性

まで提示する。

---

# 15\. エージェント利用上のルール

サブエージェント機能が利用できない環境の場合は、同じ役割をMain Agentが工程ごとに明示的に切り替えて実施する。

つまり、

実装
↓
Game Feel Review
↓
QA Review
↓
修正
↓
再テスト

を必ず分離する。

実装直後に「問題なし」と自己判断して終了しない。

---

# 16\. テスト方針

最低限、

`npm run build`

が成功すること。

可能なら、

- unit test
- Playwright
- 複数画面サイズ
- タッチ相当入力
- キーボード入力

も確認する。

ブラウザ実行環境が利用できない場合は、その旨を記録し、人間によるプレイテスト項目を明確に残す。

---

# 17\. Game001の目的

Game001は完成品であると同時に、

「今後100ゲームを作るための研究用ゲーム」

でもある。

Game001終了後、必ず

`GAME001_LESSONS.md`

を作成する。

内容：

- 良かった構造
- 共通化候補
- 共通化すべきでないもの
- 実装しづらかった部分
- テストしづらかった部分
- 今後改善すべき開発フロー
- 人間によるプレイテスト結果
- Game002で試すべき改善

Game001を基準として盲目的に全ゲームを同じ構造にしない。

---

# 18\. 最終目標

理想的な開発フロー：

```text
既存ゲームデータ
        ↓
Concept Agent
        ↓
新ゲーム企画
        ↓
Main Agent
        ↓
Gameplay Engineer
        ↓
Game Feel Reviewer
        ↓
QA
        ↓
自動修正
        ↓
Preview
        ↓
人間プレイテスト
        ↓
公開
```

Codexが大量にコードを書くことではなく、

「面白いゲームを効率よく継続追加できる開発システム」

を作ることを最終目標とする。
