診断は読み取りのみ。状態変更・強制死亡・時間加速で高スコアを作っていない。保存値を 1 CREDIT にする準備は、最悪カードを確認する UI fixture として明記し、3 回自然終了した実行と区別した。ヘッドレス環境では長いフレームを抑制するため、壁時計とゲーム時間が異なる。003 の 14 階は約 197.6 実秒かかっており、一般スマホの性能を示す測定ではない。

新作の初心者目標は 45〜50 秒程度で、企画全体の基本目安「1 CREDIT 1〜3 分」より短い例外になり得る。実際の 3 CREDIT の時間・終了理由を人間で測り、必要なら調整する。広告機会のために待ち時間を追加しない。

## 全5ゲームで有効だったもの

- 描画から独立した TypeScript モデル。衝突・予告・支持・列・分類を、通常の公開操作で検証できた。
- 保存、CREDIT、RewardAdapter、生成音、Telemetry の小さな境界。特定サーバーや広告 SDK をゲームロジックへ持ち込まなかった。
- 失敗確定時の保存と一度だけの CREDIT 消費。結果演出と財布の更新を分離し、開始・pause・途中退出は無料にした。
- 自己ベスト、すぐ読める結果、再ロード不要の retry。単位は points / m / FLOORS / LEVEL / SORTED を維持した。
- 可視性・blur・BFCache に応じた停止、明示再開、mute 保存、入力の二重計上防止。保存不能時もページ内メモリで継続できた。
- ゲーム ID 付きの基本イベントと終了時集計。フレームごとの送信を避け、200 件のメモリ履歴に制限した。
- 実画面の独立レビューと QA。実装直後の自己判断で終えず、通常入力・結果・補充・小画面を確認した。

これは現行 5 本での技術的な再利用実績。100 ジャンルにそのまま強制する仕様ではない。

## 4/5ゲームで有効だったもの

Game002〜005 は補充後にタイトルへ戻り、PLAY で新しい RUN を始める。Game001 は補充後に自動開始する。4 本で前者を採用できたが、どちらが再プレイの気分に合うかは人間の H 項目で判断する。

Game001・002・003・005 は盤面の primary pointerdown と少数のグローバルキーを入力境界に使う。004 は 9 個の native button が中心で、click と pointerdown の対応を管理する。盤面全体への単一イベント方式を 004 に強制しない。

新作 4 本は結果の操作を原則 300ms 後に有効化。001 は約 420ms の死亡演出後に結果を見せる。短い保護時間という考え方は共通でも、終了の見せ方は一致しない。

**「4 ゲーム以上で完全に同じ UI」と確認できた再利用コンポーネントは今回抽出しなかった。** ボタンの目的・最小ターゲット・情報項目は似ていても、カード位置、盤面を残す必要、clear 記録、正解列、方向訂正が異なる。

## 共通化するとゲーム性を損なうもの

結果 Overlay で全盤面を覆うと 004 の正解再生が消える。全ゲームに回答期限を置くと、004 の記憶を反射に変える。全スコアをポイントへ換算すると、出社までの距離・積んだ個数・到達 LEVEL の意味が薄れる。002 の入力予約を 003 / 005 に持ち込むと、次の荷物を勝手に操作する。

Phaser を必須にすると固定 DOM パネルの 004 / 005 に不要なロードが増える。003 を重なった幅だけ切り取る積み上げにすると、全箱の荷重と支持を読む目的が失われる。序盤の失敗時間や難度段階を全ジャンル同じ曲線にする根拠もない。

## 修正から得た開発上の発見

002 は固定歩行速度の記録を「最速」から「到達時間」へ修正し、CLEAR 記録付きの 0 CREDIT カードを小画面に収めた。003 は危険度の接点マーカーを統一し、到着した荷物だけの落下と古い支持部の崩壊を分けた。

004 は Chromium の click.isPrimary が primary マウスでも false になる実例を受け、pointerdown のセル・LEVEL 承認を click と照合した。005 は同じ考えを荷物 ID に適用した。004 の小画面 pause、005 の結果・補充中のカードも修正した。タイトル・結果だけでなく **pause / 補充要求中 / 最長の説明 / 保存済み 0** を凍結前のチェックに含める改善が必要だった。

レビュー中の UI 修正は、ブラウザを止めた短い修正時間を設けてから実施。HMR を跨いだ長いプレイを合格証拠にせず、変更箇所を再検証した。テスト自身の誤り（native 2 本指の click を必ず期待、HTTP 304 の body 取得、reload のたび CREDIT を上書きする fixture）も分けて修正した。

## 検証結果と限界

TypeScript と全 5 ページの build 成功。Unit **53 件成功**。Game002 / 003 / 004 / 005 の独立 browser QA はそれぞれ **11 / 10 / 12 / 10 の異なる実行ケース成功**。Game001 は今回の cached lifecycle 回帰を含む 8 ケースが成功。project 展開で重複するケースは意図して skip し、件数に加算しない。詳細は各 QA 報告を参照。

003 は 5 seed × 60 箱のモデル確認。描画は付近の箱だけ、重心判定は着地時 O(n)、累積高さは O(1) 更新。これは実機 FPS の測定ではない。Phaser 共有 chunk は約 1.21 MB / gzip 334 KB で Vite のサイズ注意が残る。外部素材は使わず、004 / 005 の実際の取得 JS はそれぞれ **19,866 / 22,128 bytes**。HTTP 応答 body の確認で Phaser の署名・chunk 要求なし、開発 hook なしを検証した。

一般スマホの 60fps、音の聞き心地、初見の平均時間、再挑戦率、Reward 選択率、翌日再訪率は未測定。console / メモリ Stub から実際の利用者指標を算出したという主張はしない。
