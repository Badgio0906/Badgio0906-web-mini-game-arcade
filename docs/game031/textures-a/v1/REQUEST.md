==================================================
0. 今回の目的
==================================================

既存Game031のブロック表面を、ユーザーが上記フォルダへ保存した8種類の画像へ差し替える。

採用する方向はA案：
「リアル寄りスタイライズ」

目指す見た目：
・土の粒、石の割れ目、苔、結晶などの質感が分かる。
・写真のような超リアル表現までは追求しない。
・ブロックの種類と境界が読みやすい。
・落ち着いて長時間遊べる。
・PCとスマホのブラウザで、掘る・置く操作が重くならない。

今回の画像は参考に眺めるだけではなく、
加工・最適化したうえで実際のゲーム内テクスチャとして使用する。

「画像を確認し、それに似た従来の低解像度模様を作った」
だけで完了にしない。

今回の対象：
・8種類の素材画像の取り込み。
・テクスチャの最適化。
・正しいBlockIDとの対応。
・UV、フィルタ、色管理の調整。
・素材を見やすくする最小限の描画・照明調整。
・ホットバーの素材見本。
・実画面での確認。
・負荷、操作、保存の回帰検証。
・公開サイトへの反映。

対象外：
・新作の追加。
・ワールド再生成。
・ゲームルール変更。
・クラフト、敵、水、人物、手、腕、道具モデルの追加。
・Three.jsから別エンジンへの移行。
・広告、CREDIT、Analytics本番設定の変更。

フォルダ名の「掘って、埋める」は素材の保存先名。
これを理由に、現在のゲームタイトルを変更しない。

4. 素材について過大な前提を置かない
==================================================

今回提供された8枚は、見た目の色・模様を持つ画像である。

これだけで以下が揃っていると扱わない：
・正確なNormal Map。
・実測されたRoughness Map。
・実測されたHeight Map。
・物理的に正しいAO Map。
・Emission Map。
・完全に継ぎ目のないタイル画像。

ファイル名に「seamless」が含まれていても、
継ぎ目がないことは実際に並べて確認する。

今回のA案では、8枚を主にBase Color用として使う。
必要なら弱い補助マップを派生制作してよいが、
元画像から推定したものであることを記録する。

色が明るい部分が、必ず立体的に高いとは限らない。
元画像の明度をそのまま高さ・AO・金属度へ流用しない。

深部岩の画像は、他素材より粗い四角い模様に見える可能性がある。
まず実際の縮小・ゲーム表示で比較する。
その粗さを、他の7素材まで粗くする理由にしない。

今回の素材だけでは補えない品質差が残った場合は明示する。
無断で別画像へ入れ替えて「全て提供素材を使用」と報告しない。

==================================================
6. 配信用素材の制作
==================================================

まず各元画像の以下を確認する：
・実際の寸法。
・形式。
・カラーモード。
・透過の有無。
・ファイルサイズ。
・SHA-256。

1024×1024等と決めつけない。

■ 初期解像度

標準：
素材1種類あたり512×512を出発点。

軽量：
素材1種類あたり256×256を出発点。

原画像を不必要に拡大しない。
標準で不足する場合だけ、実画面と負荷を確認して変更する。
最初から全素材を2K／4K配信しない。

縮小は高品質な方法を使う。
意図せずモザイク化するNearest縮小を使わない。

■ 形式

Base ColorはWebP等のブラウザ対応形式へ最適化してよい。
色の破綻、結晶のにじみ、圧縮の格子模様を比較する。

Normal等のデータ画像を作る場合は、
Base Colorと同じ圧縮設定を無批判に使用しない。

KTX2等のGPU圧縮は、既存環境で適切に導入でき、
実際の効果がある場合の選択肢とする。
今回の差し替えを止める必須条件にはしない。

■ 配置例

既存の配置規則がなければ：

public/assets/game031/textures-a/v1/

等へ、配信用素材と必要なmanifestを置く。

元画像のフルコピーやQA一覧画像は配信しない。
アトラス方式の場合、通常プレイで個別画像とアトラスを両方重複読込しない。

元画像→加工→配信用ファイルの対応を残す。
Windowsローカルパスをブラウザから参照するコードは作らない。

==================================================
7. タイルの継ぎ目と繰り返しを確認する
==================================================

各素材を、最低3×3で繰り返して確認する。

見ること：
・左右・上下の境界に線が出ないか。
・端だけ明るい／暗い帯がないか。
・模様の切れ目が目立たないか。
・一枚の画像の照明方向が強く焼き込まれていないか。
・繰り返しによって格子模様が強く出ないか。

必要な補正：
・端のつながりの調整。
・局所的な明るさの調整。
・繰り返しを強調する端部の軽い補正。

元画像の特徴を大きく変えない。
全面ぼかしで継ぎ目を隠さない。

ランダム回転・反転は必須ではない。
継ぎ目やNormalの向きを壊す場合は使用しない。

配置後の模様を安定させる：
・カメラが動いても模様がずれない。
・Chunk再生成で模様が毎回変わらない。
・保存復元後に無理由で模様が変わらない。
・隣接Chunkにまたがる同じ素材の密度が一致する。

==================================================
8. UVとアトラスの更新
==================================================

初期基準：
1ブロックの1面に、素材画像1回分。

同じ素材の上面・側面・下面には、
まず同じ画像を使用してよい。
今回は苔土の上面だけを別の草画像へ置き換える必要はない。

苔土の側面へ土画像を混ぜる等の別仕様は、無断で追加しない。

■ UV

・6面すべての向きを確認する。
・上下反転や意図しない鏡像を確認する。
・面ごとに極端な拡大率の差を作らない。
・長い面へ結合する場合も、画像を1枚だけ引き伸ばさず、
  ブロック単位の密度を維持する。
・Geometryの面番号とBlockIDを混同しない。

■ アトラス

既存のChunk単位描画と、共有Materialを可能な限り維持する。

新画像を使うために：
「1ブロック＝1Mesh」
「1面＝1Material」
へ戻さない。

アトラスを使用する場合：
・タイル位置をmetadataで管理する。
・旧32px等の固定値を残さない。
・タイル間に適切な余白を設ける。
・余白へ端の色を延長する。
・UVを有効領域へ正確に割り当てる。
・空気と境界材のスロットを正しく区別する。

通常のアトラス全体への自動mipmap生成だけで、
隣の素材色が混ざる可能性を無視しない。

特に：
白石の端へ青結晶の色がにじむ。
土の遠景へ紫が混ざる。
という状態を確認する。

タイル単位のmipmap、適切な余白、LODの扱い、
または対応可能な別の共有テクスチャ方式など、
実装環境で安定して使える方法を選ぶ。

アトラス全体へのRepeatWrappingを、
「各タイルの繰り返し」と取り違えない。

解決のために遠景フィルタを全面的に無効化し、
画面全体がちらつく状態へ戻さない。

==================================================
9. フィルタと色管理
==================================================

Base Color：
sRGBとして扱う。

Normal／Roughness等の数値データ：
色画像としてsRGB変換しない。

rendererの出力色管理と整合させる。
二重ガンマ補正、二重色変換をしない。

■ 元画像の色を潰さない

カラー画像を使うMaterialは、基本色を白から開始する。

元画像へさらにBLOCKSの旧色を強く乗算し、
全素材が青緑や茶色へ濁る状態を避ける。

既存のvertex colorが単なる面の陰影なのか、
素材色そのものなのかを確認する。
照明を追加する場合は陰影の二重掛けを避ける。

■ フィルタ

A案では、粗いドットを強調する設定を目的にしない。

初期方針：
拡大：LinearFilter
縮小：適切なmipmap付きフィルタ

アトラスのにじみ対策と併せて設定する。

異方性フィルタは、端末が対応する上限内で控えめに使う。
初期目安は軽量1～2、標準2～4程度。
最高値を無条件に指定しない。

面の斜め見、遠景、移動中のちらつきまで確認する。

==================================================
10. マテリアルと最小限の照明調整
==================================================

まず提供画像を正しく表示する。
その後、素材感を出すために必要な最小調整を加える。

現在MeshBasicMaterialを使用している場合、
ライトを追加しただけで素材の陰影が変わる前提にしない。

■ 標準設定

MeshStandardMaterial等の光に反応するMaterialを採用してよい。
既存の構造を尊重し、過剰な描画機能を追加しない。

変更する場合：
・Geometryへ正しい面法線を設定する。
・ブロックの面は平らに保つ。
・角を丸めるための形状変更はしない。
・隣接面を滑らかに平均化して、立方体が丸く見える状態にしない。

初期の基本：
・metalnessは0。
・roughnessは高め。
・弱い環境光。
・方向が分かる程度の光。
・地下の最低限の明るさを確保。

全体に1つの粗さで十分な見た目になるなら、
最初から素材ごとに多数の描画パスを分けなくてよい。

必要に応じた調整目安：
苔土・土・白石：粗さ高め。
石・深部岩：粗さ高め、わずかに硬い質感。
青結晶・暗色結晶：石より控えめに滑らか。
琥珀鉱：母岩は粗く、鉱脈部分だけ少し艶を感じる。

これらは見た目の調整目安であり、実測した物性値ではない。

琥珀色だからといって全面金属にしない。
青結晶をガラスのような完全透明材質にしない。

■ 軽量設定

同じ提供画像を縮小した版を使う。

軽量化のため、
Basic系の描画と控えめな面陰影を使うことは許容する。

ただし、軽量設定だけ元の単色模様へ戻し、
提供画像が全く反映されない状態にはしない。

■ Fog

青緑のFogが近距離の全素材へ強く掛かり、
白石・土・岩の色差が失われていないか確認する。

近距離の素材色を読めるよう、必要な範囲で調整する。
遠景を隠すためだけに、すぐ目の前から濃霧を掛けない。

今回、昼夜サイクル、天候、リアルな暗闇は追加しない。

==================================================
11. Normal・発光等は必要な範囲だけ
==================================================

必須の完了条件は：
8枚の提供素材が適切に表示され、
以前より素材の違いと質感が明確になること。

追加のPBRマップ制作そのものを目的にしない。

■ Normal／Bump

必要なら弱い補助マップを生成してよい。

・Base ColorをそのままNormal Mapへ指定しない。
・明度から推定した凹凸を、実測形状と呼ばない。
・薄い苔や小石が大きく盛り上がって見えないようにする。
・粗い深部岩の模様を、巨大な段差として強調しない。
・継ぎ目も確認する。
・UVの回転／反転と凹凸の方向を一致させる。
・効果が悪い素材では使わない。

■ 発光

青結晶、琥珀鉱、暗色結晶に、
必要なら弱い局所的な発光を追加してよい。

母岩まで全面発光させない。
色から作った選択マスクを使用する場合は、
本当に結晶部分だけに効いているか画像で確認する。

発光は、
「その表面が少し明るく見える」
程度を基本とする。

全結晶をPointLightにしない。
強いBloomで模様を消さない。
発光で周囲を照らす高度な仕組みは今回不要。

■ 今回実装しないもの

Displacementによる地形形状変更。
Parallax Occlusion Mapping。
透明ブロックの屈折。
リアルタイム反射。
動的GI。
SSAO等の新規画面効果の大量導入。
高解像度の動的影。
テクスチャのための衝突形状変更。

==================================================
12. ホットバー・選択表示・粒子
==================================================

ホットバーの素材見本も、新しい素材に合わせる。

・新テクスチャの小さな見本。
・日本語名。
・所持数。
・選択中の強調。

小さな3D見本が必要でも、
各スロットごとに別のWebGLRendererを作らない。
2Dサムネイルや既存の表示機構を使う。

同じアトラスをCSS等で使える場合は再利用してよい。
小アイコンのために元の高解像度PNGを全て再読込しない。

青結晶と石、白石と土などが、
縮小時にも見分けられるようにする。

掘削枠、ヒビ、進行表示、配置プレビューは維持する。

・白石の上で白い枠が消えない。
・暗色結晶の上でヒビが見えないままにならない。
・有効／無効の配置プレビューを区別できる。
・画像のひび割れ模様を、採掘進捗のヒビと混同しない。

必要なら輪郭へ暗い縁を加えるなど、
コントラストだけを調整してよい。

粒子色は新素材と極端に食い違わないよう微調整可。
粒子数や寿命を増やして重くしない。

==================================================
13. 読み込み・失敗時・品質切替
==================================================

素材は同一ゲーム内で共有して読み込む。

・Chunkごとに画像を再取得しない。
・掘るたびに画像をCanvasへ描き直さない。
・毎frameでtexture.needsUpdateを立てない。
・ブロックごとにMaterialを複製しない。
・画質変更ごとに使わないTextureを蓄積しない。

標準／軽量の切替では、
新しい素材の準備が整うまで現在の正常表示を維持してよい。

古い読み込み結果が後から到着し、
最新の品質設定を上書きしないようにする。

タイトルへ戻った後やRenderer破棄後に、
古いPromiseが破棄済みMaterialへ画像を設定しないようにする。

■ 読み込み失敗

通信エラー、404、画像decode失敗を扱う。

通常利用者には、
必要なら既存の簡易素材へ安全にフォールバックして、
ゲームと保存を壊さないようにしてよい。

ただし開発・公開確認では、
フォールバックを「新素材読み込み成功」と扱わない。

素材読込状態とエラーを確認できるようにする。
無限待機、無限再試行はしない。

==================================================
14. パフォーマンス条件
==================================================

テクスチャ改善によって、
掘削・配置・移動が目立って重くなることを避ける。

確認する数値：
・追加の初回転送量。
・素材ごとの解像度とファイルサイズ。
・実際に読み込むアトラス／Texture数。
・概算GPUテクスチャメモリ。
・draw call。
・Geometry／Texture数。
・frame time。
・Chunk再構築時間。
・編集から描画反映までの時間。

PNGをWebPへ変換して通信量が減っても、
同じ解像度ならGPU側の使用量まで同じ割合で減ったとは判断しない。
解像度、形式、mipmap、圧縮方式を分けて記録する。

アトラスに大きな空き領域を作りすぎない。
不要なマップを追加して、見た目の差が小さいままメモリだけ増やさない。

標準と軽量の両方で確認する。
スマホだけ画面解像度を極端に落として、素材改善を見えなくしない。

改善前後を同じ条件で比較する：
・同じ端末または同じ検証環境。
・同じviewport。
・同じ世界状態。
・同じ位置と向き。
・同じ品質設定。

数値が悪化した場合は、原因と採用した対策を残す。
実機未確認なのに、全スマホで快適と保証しない。

==================================================
18. Jevと証拠の扱い
==================================================

現行docs/JEV_REVIEW_RULES.mdを使用する。

Jevは、実際に見つかった問題の仕分けに限る。

例：
・ファイルは読めたがブロックが真っ白。
・Chunk端だけ他素材の色がにじむ。
・軽量設定だけ極端に暗い。
・品質切替後にTexture数が増え続ける。
・画像差し替え後、旧世界を開けない。

画像の見た目を、Jevが直接見て評価したと報告しない。
Visual確認は実画面を見て行う。

単純なHTTP200、ファイル数、SHA一致をJevへ送る必要はない。
Jevの点数や信号を、公開許可や人間の満足度に置き換えない。

実行記録は別々の出力先へ残す。
before、after、公開後を同じ画像名で上書きしない。
修正後の画面を修正前の証拠として使わない。

新素材が実際には読み込めず、
旧fallbackの画面を見て公開確認成功としない。

ユーザーPCの素材フォルダがなくても、
公開サイトとCIが正常に動くことを確認する。
