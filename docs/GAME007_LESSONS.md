# Game007 開発メモ — まだ乗れます ～ELEVATOR OVERLOAD～

2026-10-04。独立モデル QA は7/7成功。通常入力による独立 Game Feel はPASS、別工程のVisualは85/100（F12/H13）。技術ブラウザQAは6件のdistinct native testと8件の補充待機プローブに合格。人間 A〜N はすべて未実施。

## ルールと違い

450kgのエレベーターへ今回の客を乗せるか見送るか。現在荷重だけでなく、実際の次の客の重量・行先・価値、現在の名簿と次の降車階を常に表示する。荷重が減るのは目的階に着いたとき。単に足せるなら全部乗せる戦略より、次の客へ容量を残す選択が得になる場合を作る。

序盤の具体例：1F会社員65kgは4Fまで、2F来客90kgは6Fまで。3Fの台車240kgは9Fまで、価値160点。見えている4F配達員85kg＋観葉植物220kgは6Fまで、価値400点。3Fで台車を乗せると4Fに会社員が降りても330kgが残り、次の305kgは入らない。見送れば4Fに90kgが残り、395kgで配達員と植物を運べる。選択の効果を荷重・行先・得点として実際に説明できる。

NEXTは先に生成した本物の次の客であり、次階で同じID・重量・行先になる。見せた後に都合よく生成し直さない。後半は7種類の人物/物体と配達員の組合せを使う。出現する種類は8Fと14Fで増えるが、各荷物の重量はコードの数字で明示し、絵から推測させない。

## 得点と時間

配送価値は降車が完了したときだけ加点する。会社員100、配達員100、来客110、台車160（荷物4個）、植物300、コピー機340、冷蔵庫400。実際に届けた人数/荷物数も別集計する。乗客を載せた階間移動では `10 + round(load/450*20)` の運行/積載効率点を加える。空の移動は0点。効率は占有した階間の平均荷重率で、空運行を除く。

全員を断っても終了や罰はない。0点のまま進める。判断時間切れはその客を自動で見送り、配送機会を失う。勝手に過積載や減点にしない。

普通の判断時間は7秒から4.5秒まで、高速は20Fの3.2秒から2秒まで。閉扉0.4秒、通常移動1.15秒/高速0.58秒、降車表示0.45秒。時計はモデルの実際の進行時間で、ポーズ・選択中は停止する。長いフレームを50msで制限し、復帰時に経過をまとめて進めない。

20Fに到着して運行点と降車点を確定した後、一度だけ停止して乗り換えを提示する。「このまま」は通常、「高速へ」は以後の配送/運行点1.5倍。既存得点へ遡って倍率を掛けない。判断時間と階間移動だけ速くし、積載上限・配送行先は変えない。選択直後は降車0.45秒と短い入力保護350msを設け、同じジェスチャーで次の客を乗せない。

## 超過の確定と警告

合計が450kgを超える乗車入力で、そのRUNの結果を即時確定する。ちょうど450kgは合法。Boardは同じ入力処理でonEndを一度だけ通知し、UIはCREDITとログを直ちに確定する。そのうえで650ms、扉と過積載kgの警告を読み、結果カードへ進む。警告中のポーズ/TITLEでCREDITを取り消せない。事故・落下・圧迫描写は使わない。

## 素材・UI・構造

Art Director が実生成原本と最適化素材を確認した7個のWebPを使う。会社員/配達員/来客、植物/コピー機/冷蔵庫/段ボール台車、合計88,394bytes。底中央アンカー、足や車輪まで含む。コードで古いワイン色の扉・真鍮枠・床・荷重表示を作り、かごに実際の乗客を描く。見える物体はDesktopで最大6個、Mobile/短いLandscapeで読みやすい3個。残りは各画面で正しい件数表示を置き、全員の重量/行先名簿へ記録する。画像失敗時は物体名を残す。

Native DOMを採用し、Phaserを新規依存へ含めない。Gameplay Engineer が contracts/ElevatorRun/ElevatorBoard/resultFlavor/metadata を担当。UI Engineer は main/style/HTML。Main は方針と統合、QA・Feel/Visualは独立担当。Boardはかご、今回/NEXT、名簿、左右入力だけを所有する。mainはナビゲーション、開始/結果/選択、共有サービスを所有する。

Boardはprimary pointerdownの左右半面とネイティブ左右ボタン、Arrow/A/Dを受ける。ボタンを半面入力から除外して二重適用しない。click.isPrimaryを信用せず、pointerdownの承認をpointer ID/客IDで保持する。Enter/Spaceの保持は客IDの開始時承認で検証する。閉扉・移動・降車・選択中は入力を予約しない。ポーズ、タイトル、リトライ、選択、終了で承認を捨てる。AbortController/RAF破棄でイベントを残さない。

DOM更新は床・荷重・客・名簿・段階の署名が変わるときだけ。時計/扉の表示は別署名で更新する。画像と名簿の数は現在のかごとNEXTだけで、履歴を積み続けない。モデルinspectionは全パーティーとitemsの深いコピー。テスト用の強制終了/強制乗車/時間加速はない。

## 初稿の検証・課題

`npm run check` 成功。独立 QA は、実際の公開入力だけでちょうど450kgを運行し、その後の超過を入力時点で確定、降車順序とNEXT生成一回性、3F容量予約の機会費用、全拒否1000Fで0点、20F停止/未来点1.5倍/リセット、5seed300Fの保持数、コピー/長フレーム/入力連打を検証した。公開入力だけで70Fまで進むモデル試走では、全拒否0点、入れる客をすべて入れる方針8029点、3Fで容量を予約する方針8436点になった（固定の後半客選択条件、同じ110.37秒）。これは選択に得点差があるモデル例で、人間の暗算力/楽しさ/速度の測定ではない。無条件に受け入れる方針は4Fで635kgになり、185kg超過として同じ入力で結果が確定する。

難しかった点は、NEXTの生成を本番と一回に揃えること、階到着の運行点→降車→荷重→次客→20F停止の順序、ネイティブclickとキー保持の一回性、目標階前の客を配送済みと数えないこと。共通化候補は既存Storage/Credit/Audio/Telemetry/Rewardのみ。配送/容量/NEXT/名簿/DOMかごはゲーム固有として残す。

独立テストは容量境界、機会費用、実際の降車得点、NEXT一致、全拒否/timeout、20F停止/将来1.5倍、純粋実時間、長い階数での保持数、native/touch/keyboard/credit/warning、モバイル名簿と視認性を扱う。独立レビューで入力時間と難易度、画像の縮小、過積載理由の読みやすさを確認する。設計目安は初心者55秒/経験者120秒で、人間の自然失敗時刻は未測定。

## 独立実プレイから分かったこと

[Feel](ten-game/reviews/GAME007_FEEL.md) と [Visual](ten-game/reviews/GAME007_VISUAL.md) は別工程で評価した。通常の左右入力で3Fの台車を拒否し、4Fの配達員と植物305kgを載せる容量予約、その後の降車を確認した。PCは20F/1809点を43.7517秒、phoneは20F/1883点を44.5706秒で獲得。高速選択は既得点を保ち、以後の配送に1.5倍を適用した。phoneでは自然な過積載を3回起こしてCREDIT0とStub補充も確認した。これはreadonly計画で選ぶ実入力であり、人間の判断速度や楽しさの実測ではない。

実画面で3桁の重量が列幅からはみ出す問題、低いPC画面の高さ、横向きfooterの余白を見つけた。数字を小さくする前に、kg列を内容幅にし、かごの高さと装飾余白を修正した。普通の1〜4F操作で本当に305kgの客を表示し、phone4サイズで数字の単一行・カード内包を再確認。PC4サイズの実ポーズと最終横向き2サイズでも画面内に収まった。最終横向き画像は65kgの実状態であり、305kgに差し替えたfixtureではない。素材は再生成せず、初回artwork評価85を技術修正後も維持した。

次のゲームでは開始画面だけでなく、長い数字、途中選択、結果、補充待機の全状態へ高さ予算を与える。fixed列へ大きな数字を置く場合は、文字の実幅と単位まで確認する。UI修正でゲームの容量・得点・難易度を調整しない。技術QAでは実20F/46.323秒→高速→25Fの未来配送→自然な29F過積載→通常retryを確認した。連打確認でlocator.tapがenabledになるまで次階へ待つテスト側の問題は、同じ座標への即時native touchscreen入力へ修正し、元の失敗を保持した。技術QAの最終記録は [GAME007_QA.md](ten-game/QA/GAME007_QA.md) を参照する。
