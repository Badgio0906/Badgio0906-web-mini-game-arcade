候補はそのRUNの値であり、保存済みBESTを共有候補に代入しない。各ゲームの練習分岐を抜けた後、本番の既存 `run_start` 箇所だけで共有セッションを開始する。024/029の途中プレイは、新しい本番開始時に作った共有専用UUIDとローカルだけの対応印が一致する場合に限って同じ共有RUNへ復帰する。024の既存RUN IDおよび029の既存resultIdは対応印の照合にだけ使い、共有payloadへコピーしない。導入前の保存や対応印がない保存から共有RUNを新設せず、過去のプレイ結果を遡及投稿しない。共有済みのRUNは再読込後も再投稿しない（共通サービスの永続印と送信済み検査）。非対応Godot012〜014のコンパイル済みゲームは改変していない。

019は転落や再開で新しい共有RUNを作らない。一時停止で保存済み最大進行に対応する節目を通知でき、未送信の候補は後の節目で更新できる。いったん送信確定した同RUNは最大1回という共通サービスの制約を維持する。共有のためにGame Overや終了画面を追加していない。

031は非競争の「この世界の記録」。既存IndexedDB `game100garage-game031` v1 の `worlds` storeへ `record-current` という小さいメタデータを追加する。`current`世界保存と同じtransactionで確定／削除し、失敗は双方の以前の状態を保つ。seed、world_id、配置、inventoryはこのメタデータに入れない。既存世界payloadとgenerator/block/schema版は不変。既存世界が新しいコードで実際に次回保存されたときにメタデータが作られ、ポータルのために世界やChunkを再生成しない。バックアップ読み込みも既存save経路を使うため原本とメタデータが整合する。

031対象単体44件成功（原41＋atomic metadata・成功後通知・通知失敗分離の3件）。初回fixture2件は旧one-put期待と空のMap値undefined/null差を更新し、正常保存／拒否／transaction失敗／旧版保存保全等を再確認した。これは単純なキー／件数／型の明示的契約変更の照合でありJev対象外。共有サービスが構築中の最初のtypecheckは17件のmodule-not-foundだけだった。サービス追加後の `npm run check` はexit0。build・共通サービスの機能テスト・実ブラウザ結果は統合QAで別途記録し、ここで実施済みとしない。
