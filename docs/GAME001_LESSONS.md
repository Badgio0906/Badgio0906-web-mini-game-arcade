# Game001 — ORBIT SHIFT：実装の学び

記録日：2026-10-04（日本時間）。初回実装時の記録に、今回ユーザーから報告された人間プレイテストの合格結果を追記しています。

## 今回完成した範囲

Phaser + TypeScript + Viteによる静的ゲーム。1ボタンの時計回り移動と2軌道切替、検証済み障害パターン、SHARD、Near MissとCOMBO、タイトル・結果・高速リトライ・ポーズ、3 CREDITとRewarded Ad Stub、ローカル自己ベスト・音量設定、生成SE、Telemetry Stubを実装しました。オンラインランキング・サーバー・本番広告・ポータルは実装していません。

Gameplay Engineerの実装後、別担当のGame Feel ReviewerとQA / Code Reviewerが実際のChromiumでレビューしました。自動操作による難易度の確認は、初心者の反応時間や人間が感じる面白さの代替にはなりません。

## 良かった構造・実装上の発見

- シミュレーションをPhaserから分離したことで、パターンの安全性、切替中の衝突、スコア、長時間プレイを描画なしでテストできました。描画と同じモデルをブラウザテストでも使用しました。
- 障害を「単一軌道の障害を含むパターン」として生成し、最悪速度での移動時間と反応余裕をテンプレート間でも検証しました。単なる乱数より、調整箇所と安全条件が明確になりました。
- タッチ・Space・Enterを同じ入力境界に集め、Phaserの入力を無効化したことで、ブラウザのボタン操作とゲーム入力の二重発火を避けました。
- 保存失敗時にメモリへ切り替えることで、LocalStorageが使えなくてもゲームを続けられます。メモリの値を優先し、読み取りのみ許可された保存領域から古い値が復活しないようにしました。
- CREDIT消費と保存は衝突時に行い、結果画面の表示だけ420ms遅らせます。死亡演出中の退出・ポーズで消費を避けられる設計上の隙間を修正しました。
- Reward Stubの要求中フラグをサービス側にも置き、UIの連打と将来の広告SDK失敗を一箇所で扱えるようにしました。
- 生成音で外部素材の読込みをなくし、切替・SHARD・Near Miss/COMBO・死亡のフィードバックを区別しました。

## 共通化候補

候補はありますが、Game002〜Game005で必要性を確かめてから昇格します。

| 候補 | 何を再利用できそうか | 今は未確定の点 |
| --- | --- | --- |
| StorageService | 保存不能・破損値・読み取り専用への対応 | データ移行、ゲーム別の保存形式 |
| CreditService + RewardAdapter | 死亡時消費、重複防止、広告結果処理 | CREDITをゲーム別/全体で共有するか、再訪時の補充 |
| Telemetry境界 | イベントの呼出し・終了時の集計 | イベントスキーマ、バックエンド、通信失敗時の扱い |
| 一時停止・リトライのライフサイクル | 背景タブで停止、明示再開、開始/終了の一意性 | ターン制・リズムゲームで同じ契約が必要か |
| 音声ON/OFFとユーザー操作による有効化 | 設定保存・生成音の後始末 | BGM・素材音の必要性 |

## 共通化すべきでないもの

OrbitRunの角度・半径・衝突境界、2軌道の生成パターン、Near Miss候補の判定、速度カーブ、円形Graphics演出はORBIT SHIFT固有です。Game001の画面構成や140ms切替を、すべてのジャンルの固定基準にしません。今回のcontracts.tsも、完成済みの100ゲーム用SDKではありません。

## ゲーム性に影響する判断

| 調整 | 初期値・理由 |
| --- | --- |
| 最初の障害 | 到達約5.9秒。序盤に機体と操作を認識する余裕を持たせる。無操作の死亡時間は初心者の平均ではない |
| 軌道切替 | 140ms、途中の連打は無視、切替中も衝突。瞬間移動・無敵による回避は採用しない |
| 回転速度 | 0.84から最大1.62 rad/sまで連続的に上昇。無限に高速化しない |
| 障害間隔 | 序盤1.92radから最小1.28rad、パターン末尾に余裕を追加。最大速度での切替と反応余裕を確保 |
| 難易度 | 10・30・60・90秒で段階的にパターン候補を増やす。速度は連続変化 |
| スコア | 生存10点/秒、通過30点、SHARD60点。安全に遊ぶだけでも加点 |
| Near Miss | 衝突境界への到達約0.065〜0.32秒前に危険な軌道から切替し、実際の回避後に判定 |
| COMBO | Near Missで増加、100点×COMBO、得点倍率は最大8、7秒成功なしでリセット |
| 死亡とリトライ | 約85ms Hit Stop、死亡処理は即時、結果表示は420ms後。明示的なRETRYボタンは表示後すぐ有効 |
| 広告Stub | 約0.9秒後に成功として3 CREDIT付与し、次のプレイを開始。成功しないadapterでも復旧可能 |

## 実行結果とその限界

- 無操作での最初の死亡：約5.877秒。
- 実際のSpace入力で安全に逃げる自動操作：約30秒生存、1350点、Near Missなし。
- 約0.22秒前の切替を狙う自動操作：95秒以上生存、42490点、COMBO48。観測範囲に回避不能配置なし。
- Desktop、390×844、844×390での入力・表示・ポーズを確認。
- 人間の初心者・慣れたプレイヤーの目標時間、実機FPS、音の心地よさ、広告を見て続ける意欲は未検証。
- Phaser本体込みの初期JSは約1.24MB、gzip約343KB。外部画像・音声はありませんが、低速回線・実機で初期読込みを確認する必要があります。
- 技術検証の正確なテスト件数と証拠は[QA_REVIEW.md](QA_REVIEW.md)、実行画面からの判断は[GAME_FEEL_REVIEW.md](GAME_FEEL_REVIEW.md)に記録します。

## 実装しづらかった・テストしづらかった部分

1. 切替途中の当たり判定とNear Missの境界。半径だけ・角度だけでは不自然になるため、短いサブステップと補間中の範囲で判定しました。
2. 死亡演出とCREDITの責任を分離する必要がありました。描画を待ってから終了通知すると、ポーズや退出時の永続化に問題が出ます。
3. 自動ブラウザでの入力タイミングは、人間より正確です。安全性の確認には使えますが、自然な難易度を断定できません。
4. 同じ成果物ディレクトリへの並行Playwright実行でTrace後処理が衝突しました。production-test-resultsを分離しました。
5. 実装中のVite更新がブラウザ検証中にページを再読込みしました。最終テスト時はソース編集を止め、静的ビルドも別に確認しました。

## 改善した開発フロー・次回の改善

- 実装担当・Game Feel・QAの役割を分けました。Mainは画面/基盤を担当し、サービス境界・イベント・モデルのAPIを先に共有しました。
- 自動テストの観測用hookは開発環境だけにしました。本番ビルドにhookが存在しないこともブラウザで確認しました。
- 今後はレビュー前にソースが安定したチェックポイントを作り、並行実行するテストの出力先を先に分離します。
- レビューではスクリーンショットだけでなく、実際の入力・CREDITフロー・時間を記録します。表示の小ささはスマートフォン相当画面を見て修正します。
- Game002では、1ボタン・アクション以外の体験で、同じCREDIT/保存境界が無理なく使えるかを試します。Game001の操作やスコア方式をそのまま移植しません。

具体的な実測秒数・端末名・個別コメントは提供されていないため記録を補作しません。Game001の成功をすべてのジャンルに一般化せず、Game002以降の人間プレイテストは別に実施します。

## Game002〜005 追加時の保守

音声の再利用時に Game001 固有イベントが core に残っていたため、同じ効果音設定を `src/game/playOrbitSound.ts` に移した。共通 `AudioService` は生成音・ミュート・ユーザー操作による有効化・後始末だけを担当する。保存キー、操作、音程・音量は維持した。

`run_end` に全ゲーム比較用の `outcome` を追加し、既存の詳細 `reason` を残した。`run_duration` はポーズを除くゲーム内経過秒を記録する。ページキャッシュ復帰は quit と区別し、`pagehide.persisted` ではポーズだけを行う。終了記録は実際の退出または Game Over で一度に限る。追加保守後の 32 Unit ケースは成功。既存 7 件と、ページ復帰 → 再開 → 自然衝突で終了・CREDIT が一度となる追加ケースの計 8 ブラウザ確認も成功した。
