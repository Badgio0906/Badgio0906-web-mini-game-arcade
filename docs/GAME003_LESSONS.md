# Game003 — DROP TOWER 実装からの発見

Game003 の人間プレイテストは未実施。Game001 の A〜J 合格を他ジャンルの成功とみなさない。

## Game001・002 との差と面白さの核

高速で避け続けるゲームから、落とす瞬間を自分で待つゲームへ変えた。入力は DROP だけ。「今なら乗るか」「もう少し中心まで待つか」「傾いた塔へ次も載るか」という静かな判断を主役にした。

主スコアは安定して積めた FLOORS。高さ m と PERFECT bonus は別情報とし、精密な配置で階数が水増しされることはない。荷物の幅を重なり部分で切り詰めない。最初から最後まで元の幅・高さ・質量を持つ。

## 判断したゲーム仕様

- 600×720 の縦長の仮想画面。高さが伸びるとカメラが上へ追従し、左のメートル目盛りで積み上がった感覚を補う。
- 最初の 3 個は幅 176 / 172 / 168 px、左右の揺れ幅は ±38 px。広い土台と実際の支持関係によって親切にする。無敵・位置補正・自動整列は使わない。
- 4 個目以降は揺れ幅と速度を増す。幅・高さ・質量の変化は小さく制限し、横速度は無限に上がらない。
- 荷物を放したときの横速度は吊り下げ速度の 2%、最大 3 px/s。中心で放した荷物が大きく横へ飛んで意外な失敗になるのを防ぐ。影と点線は、小さな慣性・後半の軽い風を含めた着地点予測を示す。
- 落下は重力 720 px/s²。接触時には荷物の全幅が残る。中心差が 6 px 以内なら PERFECT。連続時は `100 × combo`、倍率上限 8 のボーナスを別途加算する。
- 着地後の 420 ms は荷物を落とせない。連打を次の荷物の DROP として予約しない。静かな間と、次の操作を自分で選べることを守る。
- 塔の各接触面で、その上にあるすべての荷物の質量を使って重心を求める。重心が実際の重なり支持面から 4 px を超えて外れたら、その接触は維持できない。
- 到着した荷物だけが支えられない場合は、その荷物が支持端を軸に傾いてから落ちる。下の塔は勝手に崩さない。新しい重さが以前の接触面を破綻させた場合は、その上の構造が崩れる。
- 失敗と確定したときに終了通知を 1 回送る。CREDIT 保存は結果演出待ちから分離する。荷物が落ち始めた段階では RUN はまだ進行中で、完全に塔を離れた時点で fall とする。

## 物理の範囲

Phaser Matter の本格的な剛体シミュレーターではなく、質量・支持・傾きの原因を追える決定的な toy physics とした。微細な接触ノイズや急な跳ね返りを増やさない。

積む対象は塔の最上面。側面の段に別棟を組む分岐構造はモデル化しない。着地後の小さな減衰揺れは演出、荷物の支持端からの転倒は位置と回転を持つモデルの運動として区別する。この近似が遊びやすさと納得感を両立するかは、人間に確認する。

## 再利用・ゲーム固有の境界

再利用は StorageService、CreditService、TelemetryService、Reward Adapter、AudioService の tone。保存先は `web-mini-arcade:v1:game003:`。基本イベントの形は Game002 と揃え、`tower_height / perfect_count` を追加した。

ゲーム固有なのは TowerRun の支持・重心・荷物・タイミング、TowerScene のクレーンと塔、1 ボタンの DROP 入力、FLOORS 主体の結果 UI。Game002 の左右移動・敵・街を流用しない。Gameplay Engineer はモデルと Scene、Main は方針・統合・追加レビュー、UI Engineer は HTML / CSS / UI、QA と Game Feel は独立レビューを担当した。

## 開発・性能上の発見

- 支持と累積重心は、着地ごとに上から下へ 1 回の O(n) 走査で判定できる。毎フレーム O(n²) の物理計算をしない。
- 塔全体の履歴は保持するが、描画は上から画面内の箱だけを扱い、画面下に到達したら走査を止める。高さの合計はキャッシュし、毎フレームの snapshot は O(1)。
- 本体は Graphics。文字と目盛りは固定数のオブジェクトを使い、箱が増えるたびに Phaser オブジェクトを作らない。パーティクルは短時間・少数。
- 元の荷物寸法と支えの重なりを保持することで、切り詰め式スタックゲームとの違いを自動テストでも確認できた。
- 開発診断は pose、質量、支持面、重心、直近の着地情報のコピーだけを返す。強制終了・無敵・時間加速を公開しない。
- 実機スマホでの 60 FPS は人間の検証待ち。ソフトウェア描画のブラウザ確認と通常の実機性能を混同しない。

## レビューで見つかった問題

初期の支持診断は、最小余裕と最大危険度を同じ更新条件で選んでいた。小さな箱の最小余裕と土台の正規化危険度を別々に保持し、描画する支持面・重心・危険度の整合を直した。

初期案は到着した荷物だけが支えられない場合にも、塔全体の崩壊としていた。破綻した接触の位置を区別し、新しい荷物だけの転倒・落下と、以前の支持面から上の崩壊に分けた。表示名だけ変える修正にはせず、転倒の動きと崩れる構造も変えた。

## 自動テスト・独立レビュー

初期 QA は 5 seed で 60 個の中心配置を確認し、全幅保持、PERFECT と階数の分離、連打抑止、終了通知、全接触の質量重心を検証した。診断不整合と転倒・崩壊の区別の回帰を加えたモデル 9 テストは合格。

実ブラウザ Game Feel と QA、修正後の再テスト結果は完了後に追記する。初見の面白さ、待つテンポ、もう 1 個積みたい気持ちは人間の判断待ち。

独立 Game Feel と QA は最終 PASS。実ブラウザで通常入力による積み上げ、PERFECT、荷物だけの転倒・落下、以前の接触からの崩壊、カメラ追従、CREDIT と補充、保存、各画面サイズ、production 経路を確認した。Game004 の開発ゲートを通過した。人間プレイテスト A〜J の欄は未実施のままとする。

## 共通仕様候補

再利用候補は終了時の CREDIT 保存、Reward、保存障害からの回復、生成音、共通 Telemetry と game_id、開発限定診断、画面外・BFCache に応じたポーズ。1 ボタンでも「いつ入力を受け付けるか」は Game001 と異なる。落下中・着地中の入力拒否を共通規則にしない。

支持モデル、積み上げカメラ、PERFECT ボーナス、物理の許容範囲、主スコア FLOORS は固有に残す。UI は 4 本以上で一致が確認されるまでコンポーネント化しない。

## 今回のC国モード改修（2026-10-04）

現在は受理した塔の高さが厳密に15mを超えた時に一度だけ進行を停止し、通常続行と架空のC国モードを選ぶ。C国では以後の吊られた荷物の横振りを200%、既存のPerfect BONUS獲得分を300%にする。既得点の再計算、重力・落下・支持・箱サイズの変更は行わない。FLOORSの主BESTは保持し、BONUS BESTを独立して保存する。

23段で正確に15mとなる固定乱数例ではまだ表示せず、24段15.65mで表示するモデル境界を検証した。全状態の停止、解除不能な選択、未来のPerfect2400点（元800×3）、実時計・重力の保存を含む対象23件が成功。実ブラウザの結果と独立採点は[今回のQA台帳](ten-game/QA/README.md)とreviews/へ記録する。モデル試験を人間のPerfect成功率として扱わない。

人間の今回A–Nは未実施。[共通フォーム](ten-game/HUMAN_PLAYTEST.md)で、速度と三倍BONUSの取引に迷うか、C国は精度の上達を試す楽しさがあるか、架空の建築称号は短く読みやすいかを追加確認する。
