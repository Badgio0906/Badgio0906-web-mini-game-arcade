1. 最重要原則
==================================================

100ガレの開発目的は、
単純にゲーム数を増やすことではない。

・すぐ遊べる
・操作が直感的
・上達や発見がある
・もう一回やりたくなる
・くだらない遊びも丁寧に作る
・チル系の静かな時間にも価値を持たせる

これらを重視する。

今回ユーザーは、
完成度が低いと感じた作品の非公開・非表示を明示した。

技術テストの合格やVisual評価の点数を理由に、
ユーザーの面白さに関する判断を覆さない。

一方、完成版と評価された作品は、
今回の作業で不必要に改修しない。

特にGame001、016、018、019、020、022、023、025、032は、
完成版タグ変更を中心とし、ゲーム本体を変更しない。

5. 非公開と非表示を区別する
==================================================

今回の公開状態は3種類で管理する。

active：
通常のゲーム一覧へ掲載。
ゲームURLからプレイ可能。

hidden：
通常のゲーム一覧へ掲載しない。
従来のURLからは引き続きプレイ可能。

retired：
通常のゲーム一覧へ掲載しない。
従来のURLではゲーム本体を起動させず、
退役・公開終了の案内を表示する。

現在のCatalogにhiddenがない場合は、
安全な追加を行う。

Game010の既存退役方式を参考にする。

非公開＝retired。
非表示＝hidden。

元のゲームソースや素材、保存データ、過去記録を削除しない。

hidden作品をポータルの検索・絞り込み・お気に入り優先表示で
誤って再掲載しない。

hidden作品の元URL、説明、保存、操作は維持する。

retired作品では、旧URLを404にするのではなく、
分かりやすい退役案内と「ゲーム一覧へ」を用意する。

noindex等を適切に設定する。

GitHub Pagesと公開GitHubリポジトリの構造上、
ソースそのものの完全な非公開は保証できない。
今回のretiredは「公開サイトで通常プレイできない」意味とする。

==================================================
10. Game002 速度上昇
==================================================

バイクに乗った時点の距離を基準とする。

現在の仕様では、
バイク選択ポイントは2000m付近にある。

正確な開始位置は現行モデルを正本とする。

バイクに乗ってから：

0～999m：
初期バイク速度。

1000～1999m：
第1加速。

2000～2999m：
第2加速。

3000～3999m：
第3加速。

以後1000mごとに加速段階を進める。

初期調整例：

バイク開始：
速度倍率2.0

バイク走行1000m：
2.25

2000m：
2.5

3000m：
2.8

4000m：
3.1

以後も段階的に増加するが、
実際に回避可能な上限を設ける。

この値はバランステストで調整してよい。

加速段階の切り替わりには：

・速度上昇の短い演出
・疾走感のある背景スクロール
・現在の倍率表示
・軽い効果音

を入れる。

プレイを止める長い演出は不要。

==================================================
11. Game002 得点倍率
==================================================

バイク走行距離に応じて、
獲得スコアも大きく伸びるようにする。

初期案：

バイク開始：得点倍率1.0
1000m：1.5
2000m：2.2
3000m：3.2
4000m：4.5

ただし、
到達時点の倍率を総走行距離へ一括で掛け直さない。

区間ごとの加点として計算し、
長く生き残るほどスコアが加速する設計にする。

NICE DODGE等の既存ボーナスと、
加速区間ボーナスの組み合わせを整理する。

二重に意図せぬ倍率が乗らないようにする。

倍率の表示を分かりやすくする。

例：

SPEED ×2.8
SCORE BONUS ×3.2

==================================================
12. Game002 公平性
==================================================

速度が上昇すると、
障害物の出現タイミングや予兆も変わる。

速度だけ上げ、
人間に回避不能なパターンを作らない。

必須：
・常に通過可能なレーンがある。
・必要な横移動時間を確保する。
・障害物の予兆が見える。
・2レーン連続移動が必要な配置は、
  実際の操作速度で可能である。
・ポーズ復帰で即衝突しない。
・フレーム落ちで判定が飛ばない。
・高速時にも得点計算と衝突判定が一致する。

初期速度と最終高速域を、
両方通常入力で確認する。

旧BESTは保持する。
スコア計算が変わるため、
現行ルールとの比較可否を明示し、
新しい比較版・ランキングboardへ分離する。

==================================================
14. Game003 ビル形状
==================================================

建物ごとに違うシルエットを持つ。

最低8～12種類程度。

例：
・細長いビル
・上が広いビル
・下が狭いビル
・片側が張り出したビル
・L字型のビル
・段差のあるビル
・屋上に設備があるビル
・重心が偏った工場
・左右非対称のオフィス
・低く横長の建物
・下部が細く上部が重い建物

ビルは同じ矩形の見た目だけを変えたものにしない。

実際の当たり判定・質量・重心も、
見た目の形状と対応させる。

==================================================
15. Game003 物理挙動
==================================================

必要な要素：

・重力
・回転
・衝突
・摩擦
・滑り
・積み上げ
・重心
・接触面
・支え合い
・崩壊

「一度積めば完全固定」
という単純方式にはしない。

危ういバランスで何とか立つ状況を作る。

例：

細いビルの上に、
片側が重いビルを置く。

少し傾くが、すぐには崩れない。

次のビルを反対側へ置いたことで、
全体が安定する。

このような遊びを目指す。

ただし、
物理計算の誤差で突然爆発する、
重なっているのにすり抜ける、
静止したはずの建物が延々震える、
といった問題は避ける。

実際の形状に基づくコライダーを使う。
単純な四角い当たり判定だけで
複雑な形状を再現したふりをしない。

必要なら軽量な2D物理ライブラリを検討してよい。
ただし依存・容量・安定性を比較して採用する。

20. Game015 怪鳥
==================================================

怪鳥は画面内を左右に飛ぶ。

行動：
・一定範囲を左右往復。
・少し速度差がある。
・見える位置から出現。
・進行方向が分かる。
・接触すると危険。

実装済みのbird関連処理があれば再利用する。

怪鳥が完全ランダムに瞬間移動しないこと。

怪鳥が出る前には、
短い影、鳴き声、進入予兆などを入れてよい。

怪鳥を避けるため、
一瞬待つ、下へ落ちる、
左右へ動く等の判断が発生するようにする。

ただし、待つしかない状態が長く続かないこと。

==================================================
21. Game015 移動床
==================================================

現在のmoving platformの仕組みを調査する。

出現が非常に限定的な場合は、
通常プレイ中にも適度に登場させる。

種類：
・短距離で往復する床
・少し長く移動する床
・動きが遅い床
・動きが速い床

床の動きには規則性を持たせる。

「タイミングよく乗る」
「床が動いた先を予測して落ちる」
という判断を追加する。

床に乗った際のプレイヤー移動も自然にする。
床が動いた瞬間に滑り落ちる不具合を防ぐ。

==================================================
22. Game015 ルート構成
==================================================

現在の左右交互パターンに加えて：

・中央を通る安全ルート
・同じ側で連続する足場
・短い連続落下
・移動床を利用するルート
・怪鳥を避けるルート
・長く落下するチャレンジルート

を混在させる。

安全ルートの存在を
実際の物理モデルで検証する。

移動床の位相、
怪鳥の巡回位置、
スクロール速度、
落下距離の安全性を考慮する。

すべてのルートに対して、
少なくとも合理的な攻略方法を用意する。

ベースの操作感、
キャラ、ドット絵、王冠、
音、落下スピードの基本感覚は維持する。

==================================================
25. Game024 盤面の変化内容
==================================================

単に背景色が変わるだけでは不十分。

プレイヤーが実際に移動する盤面の構造を変える。

推奨：

20×20の基本サイズは維持。

その内部で、
・通路の配置
・障害物の配置
・広い空間
・狭い通路
・開けたエリア
等が変化する。

最初は小さな障害物を少数配置し、
進行に応じて盤面の変化を増やす。

例：

第1パターン：
中央が広く、左右に小さな障害物。

第2パターン：
中央付近に壁があり、上下へ通路がある。

第3パターン：
左右に小さな迷路状の区画。

第4パターン：

==================================================
26. Game024 変化時の公平性
==================================================

最重要。

盤面が変化した瞬間に、
蛇の頭や身体の上へ壁が発生して
突然ゲームオーバーになることは禁止。

変化時には：

1. 餌を食べる。
2. 移動時計を一時停止。
3. 新しい盤面を生成。
4. 安全性を検証。
5. 短い盤面変化演出。
6. 操作可能状態に戻す。

新しい障害物を置けない場所：
・蛇の頭。
・蛇の身体。
・必要な進行先。
・有効な餌の位置。

次に進める方向が存在すること。

現在の蛇の状態で、
餌へ到達可能なルートが存在すること。

蛇の身体が長い場合は、
一時的に通路を広くするなど、
安全な配置へ調整する。

変化直後の入力が意図せず持ち越され、
即衝突しないようにする。

無限再生成にならないよう、
試行回数に上限と安全な代替生成を設ける。

蛇が成長して盤面が埋まってきたら、
障害物密度を下げる。

最終的に400マスを埋めるクリア構造を
不可能にしない。

・対象作品。
・発生工程。
・原因。
・影響範囲。
・未完了部分。
・再開方法。

を記録する。

別作品の作業に影響しないなら、
その作品だけ保留し、ほかの作品を継続する。

画像生成が使えない場合も、
素材の使用可否を正確に報告する。

成果物が存在しないのに、
生成・統合済みとは書かない。
