3. 画面遷移をまたぐ入力を重点テストする
==================================================

前バッチでは、前の画面で始まったタップから発生したclickが、
新しく表示されたキャンセルボタンへ届く問題があった。

今回も次のような場面で再発し得る。

・ショット確定直後に結果画面が出る。
・最後の得点直後に「もう一局」が出る。
・釣りの回収直後にアップグレード画面が出る。
・プラグ到達直後に「次のステージ」が出る。
・サイコロ操作直後に手番やメニューが変わる。

原則：
ある画面で開始した1つのジェスチャーを、
別の画面の新しい操作として再利用しない。

入力開始時の画面状態・世代番号・pointer IDなどを使い、
処理済み入力や旧画面の入力を区別する。

ただし、
「画面遷移後は全入力を長時間無視する」
という大きな待ち時間だけで解決しない。

また、clickを全面禁止して、
キーボードや支援技術によるボタン操作を壊さない。

必須テスト：
・押す→画面遷移→離す。
・ドラッグ→クリア→離す。
・長押し→画面遷移→compatibility click。
・pointercancel。
・lostpointercapture。
・連打。
・同じ座標に次画面のボタンが現れる。
・Enter押しっぱなしで画面が変わる。

キャンセルは、成功操作やショット確定として扱わない。
pointerupとclickで二重確定しない。

タッチの暗黙pointer captureがあることを前提に、
イベントのtargetだけでドラッグ先を判断しない。
必要な場面では実座標から対象を判定する。

touch-actionは領域と状態に合わせる。
ゲーム操作の抑制を理由に、説明・設定・盤面外のスクロールまで止めない。

4. 非同期処理・保存・終了後の復活を防ぐ
==================================================

CPU思考、盤面生成、サイコロ演出、球の移動、
巻き上げ、ステージ切替には、ゲーム世代／RUN／処理IDを関連付ける。

次の場合は古い処理を無効化する：
・新しいゲーム。
・タイトルへ戻る。
・明示リセット。
・別ステージへ移動。
・終了確定。
・処理のキャンセル。

古いCPU応答やタイマーが、
新しいRUNへ着手・加点・結果表示しないようにする。

■ 保存

次の流れを重点確認する。

プレイ
→ 一時停止
→ タイトル／ポータル
→ pagehide
→ 再読込

明示的に終了・破棄したRUNを、
後からpagehide処理が保存し直して復活させない。

継続保存するRUNと、終了・破棄したRUNを区別する。
新しいRUNを始めた後、古い保存を復元しない。

得点、取得物、勝利数、アップグレード購入は一度だけ確定する。
再読込や復元で二重付与しない。

保存拒否や破損時はmemoryへ切り替え、
古い保存値を繰り返し読み直して現在の状態を失わない。

解析同意がないことやTelemetry observerがないことを理由に、
通常のゲーム保存を壊さない。

リアルタイムの作品は、非表示・中断からの復帰で
経過時間を一度にシミュレーションしない。
復元後は明示的な再開を待つ。

5. 失敗時の記録とテスト出力先
==================================================

前バッチでは、
before画像や最終レビュー画像の一部が出力先再使用で失われた。

今回、テストの出力先は実行ごとに一意にする。

例：
QA/game027/<source-id>/<run-id>/

game_id、ソース状態、実行ID、viewportを識別できれば、
実際のディレクトリ名は既存構成に合わせてよい。

・過去runの出力先へ上書きしない。
・beforeとafterを同じファイルにしない。
・別担当が同じ画像名を使って上書きしない。
・検証スクリプトの出力先が固定されていないか実行前に確認する。

原因不明の操作タイムアウトが出たら、
次の実行で消してしまう前に、可能な範囲で保存する。

最小セット：
・ソース／buildの識別子。
・実行した操作。
・直前のゲーム状態。
・viewport画像。
・DOMの対象要素と状態。
・関連するconsole／通信エラー。
・入力イベントの短いtrace。
・使用したfixtureの有無。

秘密値、認証ヘッダー、個人情報を記録しない。

「もう一度実行したら通った」だけでは、
最初の失敗の原因が分かったことにならない。

明確なインフラ障害の再試行は可能。
ただしゲーム側の原因不明の失敗を、無記録で何度も再試行しない。

修正・再検証・評価は別の実行記録にする。
失われた過去画像を後から撮って「当時の原本」としない。
過去に呼んでいないJevを後から呼んで、手順実施済みへ書き換えない。

これを理由に大量の監査文書を増やさない。
既存collectorと簡潔な実行manifestを使い、
最初の失敗・修正後・最終レビューに必要な証拠を確実に残す。

6. 公開確認の順序を固定する
==================================================

前バッチでは、期待する公開workflowの完了前に操作確認を始め、
原因を確定できない空メニューのタイムアウトが発生していた。

次の順序を守る。

1. 統合するcommitを確定。
2. そのcommitに対応する公式workflowを確認。
3. build／deployを含む必要なjobの成功を確認。
4. 公開先に期待する版が配信されていることを確認。
5. その版に対して公開通常操作を行う。
6. 公開結果を記録。
7. 候補表の対象セルだけ「済」へ更新・読戻し確認。

別commitの成功workflowを証拠にしない。
HTTP200だけで期待する版の公開成功としない。

複数バッチが並行する場合：
・統合直前に最新mainを確認。
・他タスクの新作登録を消さない。
・古い成果物で新しい公開を巻き戻さない。
・共有ファイルの統合と公開操作は競合しない順序で行う。
・force pushや保護設定解除で解決しない。

作者未試遊でも試作公開する方針は維持する。
「人間がまだ遊んでいない」だけを理由に公開を止めない。

------------------------------
Game030：コンセントどこ？
------------------------------

ドラッグ座標をそのまま線にするだけでは、
速い指移動で壁を通過する可能性がある。

・前回位置から今回位置までの移動区間を検査する。
・プラグとケーブルの太さを考慮する。
・ケーブル簡略化の前後で壁を貫通しないか確認する。
・リサイズしても、ゲーム内の経路長を変えない。
・画面外から指が戻っても、位置をワープさせない。

引き戻し：
・どの既存線分へ戻れば巻き戻しとみなすか定義する。
・離れた過去の線分へ飛び移って長さを不正に消せないようにする。
・自己交差を許すか禁止するかを明示し、
  見た目、判定、説明を一致させる。

20ステージには、独自に作った到達可能な経路を確認する。
